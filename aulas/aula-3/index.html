A grande diferença: o Uno tem apenas 2 KB de SRAM. O ESP32 tem muito mais memória e oferece multitarefa, Wi‑Fi e Bluetooth, mas isso também traz mais consumo de memória e mais tarefas disputando os mesmos recursos.

Gerenciamento de memória

Como a RAM é organizada?

De forma simplificada, podemos imaginar a RAM dividida em três áreas, cada uma com uma finalidade:

Memória estática · .data e .bss

Variáveis globais e static. Existem durante toda a execução.

Heap

Memória pedida durante a execução, por exemplo com malloc(), new ou certas operações com String.

Stack (pilha)

Variáveis locais, parâmetros e endereços de retorno das funções.

Diagrama conceitual, fora de escala. As áreas não são necessariamente blocos contíguos nem têm tamanhos fixos; a organização exata depende da arquitetura.

Gerenciamento de memória

    
Memória estática: globais e static

    

      

        
Variáveis que existem durante toda a execução do programa. O espaço é reservado pelo compilador antes de gravar a placa.

        
int temperatura = 25;   // global com valor: .data
int contador;           // global sem valor (zero): .bss

void setup() {
  static int inicializacoes = 0;
  inicializacoes++;     // mantém o valor entre chamadas
}

        
    
          
  • temperatura vai para .data: tem valor inicial diferente de zero.
    • 
          
  • contador vai para .bss: começa valendo zero.
    • 
          
  • inicializacoes é local de setup(), mas o static faz ela lembrar o valor durante toda a execução.
    • 
        

        
Quando usar: estados que precisam persistir, contadores, tabelas de configuração, buffers de tamanho conhecido. Cuidado: ocupam RAM o tempo todo, mesmo quando ninguém as usa.

      

      

        
Chame as funções e observe
          

        

        

          
globaltotal0.data · vive sempre

          
locallocal—stack · só na chamada

          
static localvezes0.bss · persiste

        

        

        

        
static muda de sentido conforme o lugar: dentro de uma função, faz a variável durar a execução toda; fora de uma função, faz ela ser visível só naquele arquivo.

Stack: a pilha de execução

    

      

        
Como uma pilha de pratos: cada função chamada coloca um prato com suas variáveis locais; quando ela termina, o prato é retirado e o espaço volta a ser usado.

        

          
void funcaoC() {
  int x = 10;
}
void funcaoB() {
  int y = 20;
  funcaoC();
}
void funcaoA() {
  int z = 30;
  funcaoB();
}

          

            topo da pilha ↑
            

              
funcaoA()
z = 30

              
funcaoB()
y = 20

              
funcaoC()
x = 10

            

          

        

        
A chama B, B chama C: a pilha cresce. Quando C termina, o quadro dela sai e B continua de onde parou.

      

      

        
O problema: estouro de stack
No Uno, a stack divide os escassos 2 KB com todo o resto. Veja este código:

        
void processar() {
  int dados[500];   // int no Uno = 2 bytes → 1.000 bytes!
}

        

          SRAM do Uno · 2.048 bytes
          
estáticalivredados[500] · 1000 B

        

        
Metade de toda a RAM em uma única variável local. Se a pilha passar do espaço disponível (stack overflow), ela invade outras regiões e o programa se comporta de forma imprevisível.

        
Outro risco é a recursão profunda: uma função que chama a si mesma muitas vezes empilha um quadro a cada chamada.

        
Boa prática: evite vetores locais grandes no Uno, limite a profundidade das chamadas e dimensione buffers com cuidado.

Heap: memória alocada dinamicamente

    

      

        
O heap permite reservar memória durante a execução, quando o tamanho dos dados só é conhecido com o programa rodando.

        
void loop() {
  int* dados = new int[100];   // pede memória

  // utiliza o vetor...

  delete[] dados;              // devolve memória
  delay(1000);
}

        
Dois problemas
    
          
  • O heap acaba: se não houver memória, a alocação falha.
    • 
          
  • Fragmentação: pedir e devolver blocos de tamanhos variados deixa “buracos”. Há memória livre no total, mas nenhum bloco contínuo grande o bastante.

        
Como um estacionamento com 10 vagas livres espalhadas: cabem 10 carros, mas nenhum ônibus.

E a classe String?

    
No Arduino, operações com String podem fazer alocações no heap escondidas. O código funciona, mas textos que crescem e diminuem a cada volta do loop() geram muitas alocações. Com pouca RAM, isso merece atenção.

    

      
Com String · usa o heap

        
void loop() {
  String mensagem = "Temperatura: ";
  mensagem += String(25);
  mensagem += " C";

  Serial.println(mensagem);
}

        
Cada += pode pedir um bloco maior e copiar o texto. Repetido milhares de vezes, fragmenta o heap.

      

      
Com buffer fixo · consumo previsível

        
void loop() {
  char mensagem[32];         // local: fica na stack
  int temperatura = 25;

  snprintf(mensagem, sizeof(mensagem),
           "Temperatura: %d C", temperatura);

  Serial.println(mensagem);
}

        
snprintf() escreve no máximo sizeof(mensagem) bytes: nunca passa do limite do buffer.

      

    

    
Se o buffer for grande ou precisar manter o valor entre chamadas, declare-o como global ou static: assim ele sai da stack e vai para a memória estática.

O que muda no ESP32?

    

      

        
Mais memória, mas um gerenciamento mais complexo.

        
    
          
  • A aplicação usa a memória interna para variáveis, stack, heap e outras estruturas.
    • 
          
  • O FreeRTOS gerencia tarefas, e cada tarefa tem sua própria stack.
    • 
          
  • Wi‑Fi, Bluetooth e bibliotecas também consomem memória.
    • 
          
  • Algumas placas têm PSRAM extra, útil para buffers grandes.
    • 
        

        
Uma tarefa com stack pequena demais pode estourar mesmo com bastante heap livre: são áreas diferentes.

        
Serial.printf("Heap livre: %u bytes\n",
              ESP.getFreeHeap());
Serial.printf("Menor heap livre: %u bytes\n",
              ESP.getMinFreeHeap());

        
getFreeHeap(): livre agora. getMinFreeHeap(): o menor valor desde o boot. Nenhuma das duas mede a stack de cada tarefa.

Flash: onde fica o programa?

    

      

        
A Flash é não volátil: mantém os dados mesmo sem energia. Ela guarda o firmware gravado na placa: o código e os dados constantes.

        
const char mensagem[] = "Sistema iniciado";

        
Ser const não garante que a variável fique só na Flash. Isso depende da arquitetura, do compilador e do ambiente.

      

      

        
No Arduino Uno: PROGMEM
A macro PROGMEM coloca dados constantes explicitamente na memória de programa, economizando SRAM.

        
#include <avr/pgmspace.h>

const char texto[] PROGMEM = "Ola, Arduino";

        
Para textos fixos no Serial.print, o atalho é F(): Serial.println(F("Iniciando..."));

        
No ESP32, as constantes e o acesso à Flash seguem mecanismos diferentes. PROGMEM não é uma regra universal para todas as placas.

Memória sobrando, malloc falhando

    
Depois de 3 dias ligado, um ESP32 registra no log: free=96000 maxAlloc=7800. Nesse momento, a conexão segura (TLS) precisa alocar 16 KB de uma vez e falha. Qual a causa mais provável?

    

      
A
Vazamento de memória: o heap acabou

      
B
Fragmentação: há memória livre, mas nenhum bloco contínuo de 16 KB

      
C
Estouro da stack da tarefa principal

      
D
A Flash está cheia

    

    

      
1º voto individual → discuta com um colega → 2º voto

      
    

    
São 96 KB livres, mas o maior pedaço contínuo tem só 7,8 KB: o heap está fragmentado. Um vazamento faria o free cair, e não só o maxAlloc. A correção é parar de alocar e liberar dentro do loop() (Strings temporárias, new a cada leitura) e usar buffers fixos.

Ponteiros: guardar onde está o dado

    

      

        
Toda variável mora em um endereço da memória, como uma casa em uma rua. Um ponteiro é uma variável que guarda esse endereço: ele não guarda o dado, guarda onde o dado está.

        
int x = 25;      // uma variável comum
int* p = &x;     // p guarda o endereço de x

*p = 30;         // "vá até o endereço em p e grave 30"
// agora x vale 30

        

          
EscritaLeia como

          
            
&x“o endereço de x”

            
int* p“p guarda o endereço de um int”

            
*p“o valor que está no endereço guardado em p”

            
int& r = xreferência: um apelido para x (não pode ser nula)

          
        

      

      

        Como fica na memória:
        

          
x
30
endereço 0x100

          ◀── aponta ──
          
p
0x100
endereço 0x104

        

        
O valor de p é um endereço (0x100). Usar *p é seguir a seta e mexer em x.

        
Para que servem
    
          
  • Funções que alteram variáveis de quem as chamou
    • 
          
  • Passar dados grandes sem copiar
    • 
          
  • Percorrer arrays e textos (char*)
    • 
          
  • Acessar memória do heap (new devolve um ponteiro)

      

    

  







  

    
Ponteiros e uso seguro da memória

    
Valor × referência × ponteiro

    
A mesma função, “somar 1”, escrita de três formas. Em todas, o loop() começa com int x = 5;

    

      
Por valor

        
void somar(int v) {
  v = v + 1;
}
somar(x);

        
A função recebe uma cópia. Mexe na cópia.

        x continua 5

      
Por referência

        
void somar(int& v) {
  v = v + 1;
}
somar(x);

        
A função recebe um apelido para x.

        x vira 6

      
Por ponteiro

        
void somar(int* v) {
  *v = *v + 1;
}
somar(&x);

        
A função recebe o endereço de x.

        x vira 6

    

    
Qual usar? Valor para tipos pequenos que a função só lê (int, float). Referência quando a função precisa alterar o original, ou const& para ler structs grandes sem copiar. Ponteiro quando “nenhum” (nullptr) é uma resposta válida, ou para arrays.

  







  

    
Ponteiros e uso seguro da memória

    
Três erros comuns e como evitar

    

      
1. Usar um ponteiro nulo

        
malloc devolve nullptr quando não há memória. Usar esse ponteiro trava o ESP32 (no Uno, corrompe a memória em silêncio).

        
int* buf = (int*) malloc(TAM);
if (buf == nullptr) {
  Serial.println("sem memoria");
  return;          // não usa buf
}

        ✓ sempre confira antes de usar

      
2. Sair do array

        
O C++ não confere o índice. v[5] em um array de 5 posições escreve em outra variável.

        
int v[5];   // índices 0 a 4
// ✗ i <= 5 acessa v[5]
for (int i = 0; i <= 5; i++) v[i] = 0;
// ✓ i < 5
for (int i = 0; i < 5; i++) v[i] = 0;

        ✓ compare o índice com o tamanho

      
3. Apontar para algo que já morreu

        
Uma variável local deixa de existir no fim da função. Devolver o endereço dela é um ponteiro pendente.

        
int* criar() {
  int valor = 42;
  return &valor;  // ✗ valor morre aqui
}

        ✓ use global, static ou receba um buffer

    

    
Esses erros são traiçoeiros porque o sintoma aparece longe da causa: uma variável “muda sozinha”, o alarme dispara errado, a placa reinicia horas depois.

A mensagem de status

    
O que este código imprime no ESP32?

    
const char* status() {
  char msg[20];
  snprintf(msg, sizeof(msg), "OK %d", 42);
  return msg;
}
void loop() { Serial.println(status()); }

    

      
A
Sempre “OK 42”

      
B
Erro de compilação

      
C
Comportamento indefinido: “OK 42”, lixo ou travamento

      
D
Uma linha vazia, porque msg é zerada

    

    

      
1º voto individual → discuta com um colega → 2º voto

      
    

    
msg vive na stack de status() e deixa de existir no return. O ponteiro devolvido aponta para memória que será reutilizada. Compila, com o aviso address of local variable returned, e com otimização o GCC pode até devolver nullptr. Correções: receber o buffer como parâmetro, usar static char msg[20] ou devolver um tipo por valor.

Ausência de sinal e os limites do software

    

      

        
Sensor digital
A ausência costuma ser explícita: a biblioteca devolve um código de erro, NaN ou um valor sentinela, ou a resposta não chega. Toda espera precisa de timeout: “se nada chegar em 2 s, sensor ausente”.

        
Sensor analógico
Uma entrada desconectada flutua: capta ruído e devolve números que parecem leituras reais. Um pull-down fraco (100 kΩ) leva o pino a 0 V quando o fio solta. Se o sensor nunca entrega 0 V (faixa útil de 10 % a 90 %), o 0 vira assinatura de falha.

        
O que o software não vê
O programa só enxerga números. Um sensor travado em um valor plausível, ou com deriva lenta, é indistinguível de uma leitura correta. Isso exige hardware: dois sensores (redundância), uma referência conhecida ou um autoteste.

Robustez, temporização e recuperação

    
millis() em vez de delay()

    
delay() faz o loop() parar e esperar: durante a espera, nenhum botão é lido e nenhum alarme é tratado. millis() devolve os milissegundos desde o boot, e permite conferir o relógio sem parar.

    

      
Bloqueante

        
void loop() {
  lerSensor();
  delay(1000);          // 1 s parado
  verificarBotao();     // só a cada 1 s!
}

        
Apertou o botão de emergência? Pode levar até 1 segundo para ser percebido.

      

      
Não bloqueante

        
unsigned long antes = 0;

void loop() {
  if (millis() - antes >= 1000) {
    antes = millis();
    lerSensor();        // 1× por segundo
  }
  verificarBotao();     // a toda volta
}

        
O loop gira milhares de vezes por segundo; cada tarefa roda no seu ritmo.

      

    

    

      
Timeout: toda espera por algo externo (sensor, rede, serial) precisa de um tempo máximo. “Se nada chegar em 2 s, sensor ausente.”

      
millis() volta a 0 após 49,7 dias. Escreva sempre millis() - antes >= intervalo: a subtração continua correta na virada.

    

  







  

    
Robustez, temporização e recuperação

    
Watchdog Timer (WDT)

    

      

        
O watchdog (“cão de guarda”) é um temporizador de hardware que conta até um limite. O programa precisa zerá-lo periodicamente (“alimentar”). Se o programa travar e não zerar a tempo, o WDT reinicia o chip.

        
    
          
  • Pega o que o código não detecta sozinho: laço infinito, espera eterna por hardware, memória corrompida. Por ser hardware, funciona com a CPU presa.
    • 
          
  • Timeout maior que a volta mais lenta normal do loop(), com folga.
    • 
          
  • Alimente em um único ponto, no fim de uma volta completa. Nunca em um timer ou interrupção: eles continuam rodando com o loop travado.
    • 
          
  • No boot, leia e registre o motivo do reset: o WDT esconde o defeito se ninguém olhar.
    • 
        

        

          
WatchdogVigia

          
            
Task WDTtarefas que não devolvem a CPU. No Arduino-ESP32 vigia as tarefas ociosas; o loop() só se você adicionar.

            
Interrupt WDTinterrupções longas demais ou desabilitadas por muito tempo

            
Uno (AVR)wdt_enable(WDTO_2S) e wdt_reset(), de <avr/wdt.h>

void setup() {
  esp_task_wdt_config_t cfg = { .timeout_ms = 3000,
    .idle_core_mask = 0, .trigger_panic = true };
  esp_task_wdt_reconfigure(&cfg);  // core 3.x: já vem iniciado

  if (esp_reset_reason() == ESP_RST_TASK_WDT)

Detectar, registrar, responder

    

      
1. Detectar
Verifica e classifica. “O SD falhou ao abrir o arquivo.” Não decide nada.

      
2. Registrar
Anota o que aconteceu (serial, contador, NVS) para descobrir depois.

      
3. Responder
Decide: tentar de novo, operar degradado, ir ao estado seguro.

    

    

      

        A resposta muda o estado do sistema, visível por LED:
        

          
EstadoSignificaLED

          
            
NORMALtudo funcionandoverde fixo

            
ALERTAalgo falhou, mas a função principal continua (ex.: SD fora)amarelo piscando

            
FALHAnão é seguro operar: atuadores no estado segurovermelho piscando rápido

          
        

      

      

        Uma boa mensagem diz quando, quão grave, onde e o quê:
        
[   12345] I SD: 128 linhas gravadas
[   15012] W TEMP: leitura suspeita 1/3
[   15270] E SD: open falhou 3/3 -> ALERTA

        
I informação · W aviso · E erro. Registre mudanças de estado, não a mesma mensagem 100 vezes por segundo. Para recuperar um periférico, tente de novo com intervalos crescentes (1, 2, 4, 8 s…).

Prazo de resposta e estado seguro

    

      

        
Estado seguro é a condição em que o sistema não causa dano mesmo sem controle: aquecedor desligado, válvula fechada, motor parado. Ele é definido no projeto, para cada atuador.

        
    
          
  • Defina o prazo: o tempo máximo sem uma leitura válida antes de agir.
    • 
          
  • O prazo vem da física: o tanque sobe ~1,2 °C/s com o aquecedor ligado; de 40 a 60 °C são ~16 s. Detectar + decidir + agir precisa caber com folga nesse tempo.
    • 
          
  • Continuar usando a última leitura boa é a pior escolha: o controle age às cegas.
    • 
          
  • Sempre que possível, o estado seguro também deve valer sem software: relé normalmente aberto, termostato de segurança.
    • 
        

        
const unsigned long PRAZO = 3000;   // ms sem leitura válida
if (leituraValida) ultimaValida = agora;
if (agora - ultimaValida > PRAZO) {
  digitalWrite(AQUECEDOR, LOW);     // estado seguro
  mudar(FALHA, "sem leitura de temperatura");
} else {
  controlar(temperatura);
}

Memória

    • 
        
  • Nada de new/String temporária dentro do loop()
    • 
        
  • Buffers fixos com snprintf e sizeof
    • 
        
  • Log periódico de free, min e maxAlloc

      
Ponteiros
    
        
  • Verificar nullptr antes de usar
    • 
        
  • Índices sempre conferidos contra o tamanho
    • 
        
  • Nunca devolver endereço de variável local
    • 
        
  • Tamanho conhecido → array estático

      
Falhas
    
        
  • Faixa, taxa e valor travado para cada sensor
    •

    •

    • 
        
  • Estados normal/alerta/falha com serial e LED
